# GitHub Computer-drive (bounded object storage)

`blackthorn.computer_drive` stores versioned logical files and the agent's `/workspace` checkpoints as GitHub **release assets** in the private `jadeniran21/Computer-drive` repository. It does not use StowDrive. The repository originally contained only a README; the Python implementation lives in the existing agent project, not in that repository.

Set `COMPUTER_DRIVE_GITHUB_PAT` in a secret manager and make it available only to the process that performs uploads/downloads. Never put the PAT in a release, a source file, a URL, or a log. By default the target repository is `jadeniran21/Computer-drive`; override with `COMPUTER_DRIVE_GITHUB_REPO` if needed.

```sh
python -m blackthorn.computer_drive upload /workspace/tool.tar.gz skills/tool.tar.gz
python -m blackthorn.computer_drive list
python -m blackthorn.computer_drive download skills/tool.tar.gz /workspace/tool.tar.gz
python -m blackthorn.computer_drive remove skills/tool.tar.gz
```

Each upload creates a *draft* release, streams 128 MiB assets into it, and publishes a checksummed manifest only after all assets are confirmed. Listing releases reconstructs the path index after restart by selecting the latest **published** version of each path (GitHub's listing order and `created_at` cannot be used as a latest-version guarantee). Downloads verify each part and the complete SHA-256 before atomically replacing the destination file. Older versions remain retained until `remove`, which deletes every version of that logical path. Failed drafts are reconciled and removed where possible.

**Provider lifecycle:** On the current PandaStack tier, `persistent: true` is ignored at creation and `PATCH persistent=true` returns 403 (tier restriction). The default sandbox idle TTL is 300 seconds. The controller requests and verifies a supported 3,600-second idle TTL; while a real AI task runs, its lease touches the VM every two minutes. After an idle expiry, the next actual computer tool call creates one replacement and restores the latest GitHub workspace checkpoint. No idle-only keepalive, provider plan upgrade, or quota-avoidance rotation occurs. OFF hibernates the VM but cannot defeat its finite TTL.

**Workspace persistence:** Foreground `run_command` and `write_file` snapshot the entire `/workspace` tree to a verified private GitHub release before acknowledging durable success. This includes files created with shell commands and workspace-local Python packages installed through the supplied `PIP_TARGET=/workspace/.packages`, `PYTHONPATH`, `HOME`, and cache environment. A task after VM replacement restores the archive in 16 MiB transport chunks. `job_status` re-checkpoints changes produced by a background job when polled. The VM still needs temporary local disk to run code; GitHub release assets are **not** a mounted filesystem. System packages installed outside `/workspace`, ongoing unpolled background work, provider-side failures during a command, and files larger than available Render/PandaStack storage cannot be guaranteed durable. GitHub storage is not unlimited and an independent backup remains necessary.

**Limits / non-guarantees:** This is an object store, not a mounted POSIX filesystem; programs cannot execute files directly from it. Working files must be staged onto ephemeral local storage and uploaded again after changes. GitHub release assets must each be under 2 GiB and releases allow at most 1,000 assets; this implementation rejects files beyond that count. The default 128 MiB chunks bound memory usage and provide a much lower practical ceiling than an unlimited drive. GitHub may impose additional abuse, API-rate, retention or account limits. The index is reconstructed by paginating release metadata rather than using a separate mutable database; huge numbers of releases will be slow. GitHub recommends external object storage for generated data and is not a backup service. Keep independent backups of irreplaceable files.
